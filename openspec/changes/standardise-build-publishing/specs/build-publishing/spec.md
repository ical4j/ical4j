## ADDED Requirements

### Requirement: Ecosystem repos SHALL publish via a single mechanism

Every Gradle repository in the iCal4j ecosystem SHALL publish artifacts using the `com.vanniktech.maven.publish` plugin targeting the Sonatype Central Portal. The raw `maven-publish` plugin SHALL NOT be applied for the purpose of publishing to a remote repository, and POM metadata SHALL NOT be assembled by appending XML nodes.

#### Scenario: No repo applies raw maven-publish

- **WHEN** any ecosystem repo's `build.gradle` is inspected
- **THEN** it MUST NOT contain `id 'maven-publish'` or `apply plugin: 'maven-publish'`
- **AND** it MUST apply `com.vanniktech.maven.publish`
- **AND** it MUST NOT contain a `pom.withXml` block or calls to `appendNode` for POM construction

#### Scenario: Central Portal is configured consistently

- **WHEN** any ecosystem repo's `gradle.properties` is inspected
- **THEN** it MUST set `SONATYPE_HOST=CENTRAL_PORTAL`
- **AND** it MUST set `SONATYPE_AUTOMATIC_RELEASE`
- **AND** it MUST set `RELEASE_SIGNING_ENABLED`

#### Scenario: No repo deploys to a non-repository URL

- **WHEN** any ecosystem repo declares a deployment target
- **THEN** that URL MUST be a Maven repository endpoint
- **AND** the bare portal URL `https://central.sonatype.com` MUST NOT appear as a deployment target
- **AND** `https://central.sonatype.com/repository/maven-snapshots/` remains permitted as a snapshot *resolution* repository

### Requirement: Published POM metadata SHALL be preserved across the migration

Migrating a repo's publishing mechanism SHALL NOT alter the content of its published POM. Any difference between the POM generated before and after migration MUST be intentional and recorded.

#### Scenario: POM diff is captured before legacy configuration is removed

- **WHEN** a repo is migrated to `com.vanniktech.maven.publish`
- **THEN** a POM generated by `./gradlew publishToMavenLocal` on the pre-migration commit MUST have been captured
- **AND** a POM generated after migration MUST be diffed against it
- **AND** every difference MUST be either eliminated or documented in that repo's migration task
- **AND** the legacy `publishing {}` and `signing` blocks MUST NOT be deleted until the diff is reconciled

#### Scenario: Required POM fields survive

- **WHEN** the post-migration POM is inspected
- **THEN** it MUST contain `name`, `description`, `url`, `licenses`, `developers` and `scm` elements
- **AND** the `groupId` and `artifactId` MUST be unchanged from the pre-migration POM
- **AND** the declared dependencies and their scopes MUST be unchanged

#### Scenario: Migration is proven by a snapshot before release

- **WHEN** a repo's migration is considered complete
- **THEN** a snapshot MUST have been published from that repo's CI to the Central Portal after the migration
- **AND** that publish MUST have been signed if `RELEASE_SIGNING_ENABLED` is true

### Requirement: The build classpath SHALL NOT carry known-vulnerable BouncyCastle

Every ecosystem repo that applies the axion-release plugin SHALL ensure its buildscript classpath resolves BouncyCastle at a version not affected by GHSA-p93r-85wp-75v3, GHSA-cj8j-37rh-8475, GHSA-c3fc-8qff-9hwx or GHSA-wg6q-6289-32hp.

This requirement is satisfied either by forcing the patched version or by applying an axion-release release whose own dependencies are patched. It is build-time posture only; these classes do not enter any published artifact.

#### Scenario: Patched version resolves on the buildscript classpath

- **WHEN** `./gradlew buildEnvironment` is run in any ecosystem repo
- **THEN** every resolved `org.bouncycastle:*-jdk18on` module MUST be at version 1.84 or later

#### Scenario: The check cannot pass vacuously

A repo on axion-release 1.13.6 resolves the legacy `-jdk15on` BouncyCastle family instead, against which a `-jdk18on` force has no effect. The preceding scenario would then pass while the repo carries vulnerable 1.65. This scenario closes that hole.

- **WHEN** `./gradlew buildEnvironment` is run in any ecosystem repo
- **THEN** at least one `org.bouncycastle:*-jdk18on` module MUST appear on the buildscript classpath
- **AND** no `org.bouncycastle:*-jdk15on` module may appear on the buildscript classpath

Note: the artifact family is determined by the axion-release version, but no single minimum applies — 1.15.1 already resolves `-jdk18on`, while 1.13.6 does not. The requirement is on the resolved family, not on a version number.

#### Scenario: The axion-release version is compatible with the repo's Gradle version

A separate constraint, discovered alongside the above: axion-release below 1.20.1 calls `Provider.forUseAtConfigurationTime()`, removed in Gradle 9. A repo pairing them fails at configuration time before any task runs.

- **WHEN** a repo's Gradle wrapper is version 9 or later
- **THEN** the applied axion-release version MUST be 1.20.1 or later
- **AND** `./gradlew currentVersion` MUST succeed

#### Scenario: Version computation is unaffected by an axion upgrade

- **WHEN** a repo's axion-release version is raised to satisfy the scenario above
- **THEN** `./gradlew currentVersion` MUST report the same version as before the upgrade
- **AND** the repo MUST still compile

#### Scenario: Forcing is documented where used

- **WHEN** a repo satisfies this requirement by forcing rather than upgrading
- **THEN** the force block MUST carry a comment naming the advisories it addresses
- **AND** that comment MUST state that the exposure is build-time only

#### Scenario: The force cannot be delegated to a convention plugin

- **WHEN** build configuration is later extracted into shared convention plugins
- **THEN** the buildscript-classpath force MUST remain in each repo's own build script
- **AND** it MUST NOT be moved into a convention plugin, because a plugin cannot alter the classpath that resolved it
